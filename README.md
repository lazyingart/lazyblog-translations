LazyBlog Translations is the WordPress-side renderer and storage layer for the LazyBlog multilingual publishing workflow.

It intentionally stays small:

- stores source language and per-language post translations in post meta
- renders a floating language switcher compatible with the LazyBlog site style
- requests missing translations from Codex/LazyBlog, OpenAI, or DeepSeek
- keeps one translation job per post/language to avoid duplicate work
- renders Markdown-origin math with MathJax while avoiding heavy translation-plugin behavior

## Providers

LazyBlog Translations supports three provider modes from WordPress Settings > LazyBlog Translations:

- `Codex / LazyBlog local API`: calls a local LazyBlog API service. Use this for the full Codex workflow with polishing, Markdown sync, and richer post maintenance.
- `OpenAI direct API`: calls the OpenAI Chat Completions API directly from WordPress. Default model: `gpt-4o`. No local API service is required.
- `DeepSeek direct API`: calls the DeepSeek OpenAI-compatible chat endpoint directly from WordPress. Default model: `deepseek-v4-flash`. No local API service is required.

If you choose the Codex provider, prepare the local service from the LazyBlog repo:

```bash
scripts/install_lazyblog_translation_api.sh
```

That script creates/checks `.env`, ensures a LazyBlog bearer token exists, validates Python/Codex/tmux, and starts the API in tmux through `scripts/start_live_translation_api_tmux.sh`.

## Runtime Boundary

The plugin stores translation metadata, renders the language switcher, verifies frontend requests, and coordinates translation generation.

The Codex/LazyBlog API owns the full local automation workflow: Codex execution, prompt design, polishing, image handling, Markdown sync, and background task monitoring.

OpenAI and DeepSeek direct modes are intentionally simpler: the plugin sends the post title/content/excerpt to the selected hosted API, expects JSON output, stores the translation, and redirects the reader to the translated URL.

## Security

- Public users can request a missing translation only through a signed, short-lived request generated by the plugin.
- Admin-only REST endpoints require normal WordPress capabilities.
- Provider API keys are stored server-side only; the browser never receives them.
- The source repository must not include `.env` files, API tokens, app passwords, exported posts, or local deployment logs.
